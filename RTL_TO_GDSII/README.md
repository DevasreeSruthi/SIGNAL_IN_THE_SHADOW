## 1. PROJECT OVERVIEW

**SIGNAL IN THE SHADOW** is a digital hardware design project focused on detecting weak signals in the presence of background noise and interference.

Radar systems often need to identify weak target reflections while dealing with background clutter, noise, and short-duration interference. A weak target may be difficult to distinguish from ordinary background variations, while an isolated spike can incorrectly appear to be a meaningful detection.

This project explores a modular RTL architecture that processes an incoming magnitude signal, estimates the background noise level, derives an adaptive detection threshold, identifies candidate weak signals, applies persistence filtering, and estimates detection confidence.

The design is organized into separate SystemVerilog modules to make its functionality easier to understand, simulate, debug, and evaluate through a digital implementation flow.

The primary objective is to develop and evaluate a hardware architecture for weak-signal detection and investigate its implementation using open-source VLSI tools and the SkyWater SKY130 process design kit.

> **Important:** This project is an RTL-level radar-inspired signal-processing prototype. Its behavior must be validated through simulation, and its physical implementation results must be reported only when supported by actual tool outputs.

## 2. PROJECT OBJECTIVES

The major objectives of SIGNAL IN THE SHADOW are:

- Design a modular SystemVerilog architecture for weak-signal detection.
- Estimate background noise using digital logic.
- Generate an adaptive threshold based on the estimated noise level.
- Identify candidate signals that exceed the detection threshold.
- Distinguish persistent signal behavior from isolated spikes.
- Estimate detection confidence using a dedicated hardware module.
- Verify the RTL using Icarus Verilog and waveform inspection using GTKWave.

- Investigate performance variation under different process, voltage, and temperature conditions.

## 3. SYSTEM ARCHITECTURE

The architecture consists of five functional processing modules and a top-level integration module.

### 3.1 Block Diagram

<img width="1388" height="455" alt="image" src="https://github.com/user-attachments/assets/56697cca-03d8-4f78-859d-2bdd699a5a82" />


The exact connections, register placement, and signal widths are determined by the implemented RTL source files.

### 3.2 Noise Estimator

**RTL file:** `noise_estimator.sv`

The noise estimator processes the input magnitude and produces an estimate of the background noise level.

This estimate provides information about the surrounding signal environment and serves as an input to the adaptive threshold module.

The noise estimate is used to help distinguish potentially meaningful signals from ordinary background variations.

### 3.3 Adaptive Threshold

**RTL file:** `adaptive_threshold.sv`

The adaptive threshold module generates a detection threshold based on the estimated background noise.

An adaptive threshold allows the detection logic to respond to changes in the background environment instead of relying exclusively on one fixed threshold.

The resulting threshold is supplied to the weak-signal detector.

### 3.4 Weak Signal Detector

**RTL file:** `weak_signal_detector.sv`

The weak-signal detector compares the incoming magnitude against the threshold generated by the adaptive threshold module.

When the input satisfies the implemented detection condition, the detector identifies a candidate signal.

This stage performs the primary threshold-based detection operation.

### 3.5 Persistence Filter

**RTL file:** `persistence_filter.sv`

The persistence filter is intended to evaluate whether detection activity persists over time.

Its purpose is to reduce the likelihood that an isolated spike will be treated as a persistent target.

The actual persistence behavior depends on the implemented RTL conditions, state transitions, and register updates.

Simulation is required to verify that persistent inputs produce the intended output.

### 3.6 Confidence Estimator

**RTL file:** `confidence_estimator.sv`

The confidence estimator provides an additional indication of detection reliability based on the signals and conditions defined in its implementation.

It is intended to complement the primary detection result.

The confidence output should not be interpreted as a statistically calibrated probability unless the design explicitly implements and validates such a probability model.

### 3.7 Top-Level Integration

**RTL file:** `signal_in_the_shadow_top.sv`

The top-level module integrates the functional blocks into a single hardware design.

It provides the external interface and connects the intermediate signals between the processing stages.

The top-level module is the main synthesis and implementation target.

### 6.7 Simulation Interpretation

The normal-background and isolated-spike scenarios were reported as passing during development.

However, the persistent elevated signal scenario did not produce the expected persistent-detection result. The reported output remained `persistent=0` even while the input magnitude was approximately 15–17.

This indicates that the persistence behavior requires further investigation.

Possible areas to inspect include:

- The threshold comparison condition.
- The candidate-detection signal.
- The persistence counter or state-update condition.
- Reset behavior.
- Clock-edge and nonblocking-assignment behavior.
- Signal-width and signedness differences.
- The number of consecutive qualifying samples required.
- The connections between the detector and persistence filter.

These are debugging possibilities rather than confirmed causes.

**The design should not be described as passing every functional test until the persistent-detection scenario has been corrected and successfully rerun.**

## 9. POST-ROUTE TIMING ANALYSIS

### 9.1 Purpose

Static timing analysis evaluates whether timing paths satisfy the timing constraints defined for the design.

The analysis may include:

- Clock period.
- Clock uncertainty.
- Input and output delays.
- Setup slack.
- Hold slack.
- Worst negative slack.
- Total negative slack.
- Maximum path delay.
- Minimum path delay.
- Clock arrival and required times.

The precise parameters available depend on the flow, constraints, and report configuration.

### 9.2 Setup Timing

Setup timing checks whether data reaches a sequential element early enough before the active clock edge.

A positive setup slack indicates that the checked path meets its setup requirement under the analyzed conditions.

A negative setup slack indicates a setup timing violation.

### 9.3 Hold Timing

Hold timing checks whether data remains stable for the required interval after the active clock edge.

A positive hold slack indicates that the checked path meets its hold requirement.

A negative hold slack indicates a hold timing violation.

## 14. DESIGN CHALLENGES AND DEBUGGING

Several issues were encountered during development.

### 14.1 RTL Compatibility

Some SystemVerilog constructs required compatibility adjustments for the available Icarus Verilog environment.

The source code was adjusted in places to use more compatible procedural constructs.

This highlights the importance of checking language support when moving RTL between simulators and implementation tools.

### 14.2 Persistent Signal Detection

The persistent elevated signal test did not produce the expected persistent output.

The reported `persistent=0` result indicates that the persistence behavior requires additional debugging.

The candidate-detection signal, persistence logic, clocked updates, reset conditions, and threshold comparison should be examined together.

### 14.3 Gate-Level Model Compatibility

The GLS attempt encountered issues with standard-cell model syntax and missing cell definitions.

A compatible simulation setup must be established before the synthesized netlist can be meaningfully validated through gate-level simulation.

### 14.4 Physical-Only Cell Warnings

Exploratory timing analysis produced warnings related to physical-only cells.

The netlist, technology libraries, and timing-analysis setup must be aligned before drawing definitive timing conclusions.

### 14.5 LVS Errors

The exploratory LVS run reported unmatched nets and errors.

The reference netlist, extracted layout, power and ground connectivity, and physical-only cells must be checked before attempting a clean verification run.

### 14.6 Reporting Accuracy

Physical-design reports contain several distinct metrics that should not be interchanged.

For example:

- Die area is not standard-cell area.
- Configured clock frequency is not proven maximum operating frequency.
- Reset-removal slack is not ordinary data-path hold slack.
- Successful routing does not prove that DRC and LVS passed.
- A generated GDSII file does not by itself establish a clean physical-verification result.

Maintaining these distinctions is important when presenting the project for academic evaluation or technical review.
